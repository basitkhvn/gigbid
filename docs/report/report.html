1. Problem and constraints

A freelancer on a marketplace spends hours triaging jobs, writing tailored proposals with true claims, pricing under Connects budgets and answering clients. GigBid does the reading, matching and drafting; the human does the deciding.

Must never be automated: sending a proposal or message, spending Connects, claiming experience not in the portfolio, off-platform contact/payment, scraping. Enforced in code (section 9).

Budgets (declared in agent/config.yaml): p95 latency ≤ 60 s per job analysed/proposal, ≤ 12 000 tokens per job, ≤ USD 0.02 per proposal, ≤ 2 critic revisions, ≤ 30 graph steps. Prices in config are placeholders to verify against the provider list.

2. Architecture

Next.js UI→FastAPI (JWT, SSE)→bid graph / conversation graph (LangGraph, checkpointer)→ToolHub (per-agent allowlists, timeouts, retries, degraded mode)→Marketplace MCP Portfolio MCP (RAG) Workspace MCP; Marketplace → one port with two adapters (GigSim; official Upwork MCP, drafts only). Stores: LangGraph checkpointer (SQLite/Postgres), LangGraph Store for style/outcome memory with explicit promotion rules, app DB with versioned migrations (apps/api/migrations.py), Fernet-encrypted token table. Source: docs/ARCHITECTURE.md, docs/images/*.mmd.

Bid graph: Scout → Analyst → (Risk Assessor ‖ Fit Matcher ‖ Pricing via Send fan-out) → decide → Writer → claim verification → Critic (≤2 loops) → Compliance → interrupt() for approval → exactly-once executor (idempotency key). Conversation graph: Client Liaison drafts replies, books slots through the Workspace MCP; same approval gate.

Why each agent exists (separate nodes with different tools, models and trust): Scout is LLM-free and de-duplicates reposts; Analyst sees sanitised text only and has no tools; Risk Assessor is rules-first and the LLM may only add flags; Fit Matcher queries one requirement at a time; Writer is the only strong-model node and sees only cited evidence; Verifier removes unsupported claims before the Critic (ADR 0004); Compliance reads rules from config (ADR 0003). The graph used 922 tokens/job on the 48-job comparison versus 10–15k for the agent baselines (section 5) because most nodes are deterministic.

MCP surface: three FastMCP servers with read-only/destructive/idempotent annotations, Pydantic write schemas, dry_run, idempotency keys, an append-only audit log (SQL triggers), bearer auth, per-user rate limiting and a schema-snapshot contract test (24 tests, make test).

3. R&D question A: tool granularity

Hypothesis (H-A1, pre-registered): a coarse 3–4 tool surface loses argument accuracy; rewritten descriptions are best. Setup: 40 tool-use tasks, deepseek-flash, four designs over the same marketplace functions (evals/results/tool_design.json).

Findings, including negative ones. (i) Decomposition is the driver (+49 points when removed). (ii) Plain hybrid retrieval was worse than dense (0.418 vs 0.528): querying the whole job post with BM25 pulls keyword-heavy but irrelevant items. Hybrid only helps once each requirement is its own query. (iii) Cross-encoder ranking hurt Recall@5 (0.947 → 0.905); I kept it only as an absolute-relevance gate for "is this requirement evidenced?" (ADR 0002). (iv) Better retrieval did not mean a better reply rate. The last column is the simulator reply rate of a letter built from the top-5 items: v_best scores 0.011 while V5 scores 0.717. The top-5 items repeated one project, which the simulated client penalises as crowding; the shipped writer instead retrieves per requirement and cites distinct projects (0.739 in the X2 experiment). This column mixes retrieval with a crude letter template and a simulator, so it is evidence for the mechanism, not a measure of real reply rates. (v) Contextual retrieval V6 (0.333) was worse than naive in this corpus; I did not investigate why.

Claim verification (proposals_open_*.json): on 30 jobs (24 drafted, 6 scams skipped) deepseek-flash wrote 1.542 unsupported claims per proposal before verification and 0.083 after; deepseek-v4-pro 0.958 → 0.000. Claims per proposal averaged 4.5 before removal. Caveat: "unsupported" is judged by my verifier (deterministic matching plus semantic check), the same component that removes them, so this is a consistency measure, not an independent audit.

Shipped choice: decompose per requirement + dense/BM25 RRF + outcome boost, ranked without the cross-encoder; cross-encoder only as a relevance gate (threshold −3.0 chosen on dev-adjacent data).

6. The change request

The real 2 Nov change was not in my materials, so I simulated it: Connects cost ×1.5 and cover letter length 200–1500 characters (commit b8a7d71). It took 9 changed lines in 3 files, no Python logic, a few minutes including tests: 3 lines in agent/config.yaml, 4 in the simulator policy file, 2 test fixtures (60-character letters now below the minimum). Pricing reads the live Connects cost from the marketplace tool, and Compliance reads bounds from config.

What this says: numeric policy changes are absorbed by config plus a read-the-policy tool. A new kind of rule (e.g. max 3 proposals per client per week) would need a new check node. A side effect I only noticed later (section 8, class F3): the new 200-character minimum interacts badly with claim removal; 10 of 48 drafted open-model runs ended blocked because verification left too little text.

7. Signature extension X2: proposal experiments

Paired A/B over 180 dev jobs in GigSim (ab_experiment.json): A = per-requirement retrieval with cited projects (shipped); B = generic skills list. Reply rate A 0.739 vs B 0.422; Fisher exact p=1.6e-9, paired exact McNemar p=2.1e-8. Caveat that dominates: the simulated client rewards skill mentions and penalises generic phrasing by construction, so this validates the experiment machinery (strategy → GigSim → test), not that grounded letters win with real clients. A first version of A lost (0.19 vs 0.42) because the top-5 items repeated one project; that negative result drove the per-requirement design. Real-client outcomes were not measured.

9. Safety and platform respect

Never: send without approval; spend Connects without approval; fabricate experience; include contact details, guarantees or off-platform asks; scrape; log PII or tokens. Enforced by: LangGraph interrupt() and an executor that only runs after resume (no auto-send mode exists; autonomy can only auto-skip); deterministic idempotency keys plus a server-side store (crash-resume test shows exactly-once send); per-agent tool allowlists; PII masking in traces, logs and audit; Fernet-encrypted tokens; user_id in every app query; per-user rate limiting and scout interval ≥ 60 min; live mode only via the official Upwork MCP with human confirmation. Details and the control-to-code map: docs/SAFETY.md.

What still gets through: paraphrased injections that avoid trigger phrases, or text smuggled into screening questions, are not stripped by the regex layer; defence then rests on the model treating job text as data and on the Compliance filter. My 36 planted attacks were too easy to measure this. Verification is only as good as the portfolio: a false claim inside a portfolio document passes. Synthetic clients cannot test social-engineering replies.
